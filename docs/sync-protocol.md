# 增量同步协议草案

## 客户端写入

1. 用户操作先写 SwiftData，并将实体标记为 `pending`。
2. UI 立即成功，不等待网络或附件上传。
3. `SyncCoordinator` 把一批带稳定 UUID、base revision 和 idempotency key 的变更推送到 `/v1/sync/push`。
4. 服务端在同一事务内校验所有权、处理冲突、增加 revision，并写入 `change_log`。
5. 服务端返回最终版本，客户端据此清除 pending 或覆盖普通字段。

## 增量拉取

1. 客户端保存最后成功 cursor。
2. 请求 `/v1/sync/pull?cursor=<value>`。
3. 服务端只返回当前会话用户可见的变更和新 cursor。
4. 客户端在本地事务内应用 upsert/tombstone，成功后才更新 cursor。

## 首版冲突规则

- 普通字段：服务端最后写入优先，并返回最终实体。
- 删除：tombstone 优先，离线旧设备不能复活记录。
- 同一 idempotency key 的重试必须返回同一结果，不能重复创建。
- 附件独立重试；结构化记录同步不等待附件完成。

登录恢复、App 启动、进入前台、网络恢复和手动刷新触发同步；失败使用带抖动的指数退避。

## 附件与设备数据

- 健康记录先同步结构化字段，图片和 PDF 逐个通过私有对象存储上传，失败不阻塞记录本身。
- PostgreSQL 只保存附件元数据、对象键、上传状态、revision 和 tombstone；文件本体不进入数据库。
- 上传完成前本地文件不可清理；服务端确认后可按缓存空间策略保留缩略图并按需下载原件。
- 提醒规则参与正常增量同步，但 `UNNotificationRequest` 标识和系统通知权限属于设备本地状态，不跨设备复制。
- 临时 OCR 文本不上传；用户确认并保存为健康记录详情后，才作为普通记录字段同步。
